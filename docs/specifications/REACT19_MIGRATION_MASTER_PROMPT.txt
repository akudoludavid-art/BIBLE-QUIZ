# 09 — QUESTION EXPOSURE HISTORY, ADAPTATION, RANKING AND FAIRNESS (FUTURE CONTRACTS)

This section concerns **future architecture**, not authorization to change current quiz difficulty or to begin collecting/centralizing user data.

## 9.1 Exposure must be recorded, not guessed

Design a future `QuestionExposureEvent` shape with at least:

- Local profile/verified player ID if one exists at the time of collection.
- Canonical question ID and **question version** (plus form/version if relevant).
- Event/session ID, timestamp and encounter context.
- Displayed/answered/skipped status and verified result when applicable.
- Content/curriculum version and deduplication information.
- Optional local privacy/retention policy.

**Unknown is not zero.** Do not backfill historical exposures from ranking, earned RP, age, inferred knowledge, question count, or incomplete saved sessions. When a player's actual exposure history was never logged, keep it `unknown` rather than asserting the player has never seen the item. Prefer immutable append-only events or defensible aggregate lineage when implemented in a future release.

During this migration, define only the schema/adapter contract and, if warranted by existing data, a clearly labeled legacy mapping. Do not silently create new analytics tracking or upload existing memorisation content. Any optional new local exposure collection must be separately documented, privacy-reviewed and tested before activation.

## 9.2 Future adaptive question selection

- Standard solo rotation preserves existing measurable behavior now.
- Future adaptive strategies should use the actual student's question history, verified mastery/evidence, concept coverage and variation—not merely rank.
- Randomness should be seedable for tests; no adaptive algorithm is permitted to permanently exclude valid content accidentally.
- Define a strategy interface, not a live adaptive behavior change during migration.

## 9.3 Competitive fairness requirements to document

- Ordinary multiplayer is **standard shared competition**: all players in a match receive the same question content/conditions, with no undisclosed adaptive advantage.
- A distinct **optional Balanced Competition** may eventually be agreed to by participants for mixed-experience matches.
- Never auto-adjust simply because one participant has a higher rank.
- Only consider question-specific exposure adjustment when actual logs show the more-experienced player has encountered that particular question **at least twice** (provisional criterion), while comparing the lower-ranked player's recorded encounters too.
- Exposure to an old question version is not necessarily equivalent to exposure to a substantially rewritten question.
- Surface the mode clearly and agree on the rules; anti-gaming, fairness and exact adjustment algorithm belong to later backend design.

These rules are **documentation/contracts only** now. Do not modify current quiz selection based on this prospective policy.

## 9.4 Keep progress systems conceptually independent

- **Journey RP** measures long-term earned engagement/progression.
- **Competitive skill rating** measures demonstrated performance against other players.
- **Game score** is a per-session result.
- **Category mastery medal** requires repeated successful evidence across every applicable question form and multiple opportunities, not one high score or a repeated fixed question.
- Current draft long-term Conformer progression targets approximately **18 months minimum** of sustained participation, with policy/versioning and future community-growth adjustments; no RP/rank activation is authorized here.

Do not merge these into a single “level” property in the core quiz domain. Define separate future-facing names and interfaces/documentation only.

## 9.5 Future multiplayer security boundary

Online competitive answers must eventually be decided by a trusted server. The offline bundled quiz necessarily exposes its local question/answer data to clients and **must not be assumed secure for high-stakes multiplayer**. Document a later protected competitive bank, trusted scoring, room authorization and synchronized session design. Never build these live services within this migration scope.

Historic draft multiplayer room limits varied (for example 18 participants including host versus a later 20-player concept). **Do not freeze a room capacity into today's solo migration**; future multiplayer implementation must follow its own final signed-off spec.

# 11 — LEGACY DATA, VERSIONING, EXPORT/IMPORT AND RECOVERY (PHASE 3)

User-created Scripture content and study history are high-value data. Treat migration as a formal, reversible data transfer.

## 11.1 Understand origin separation

- An old `file://` HTML app, a local dev server and a new `https://` deployment usually use different browser storage origins/contexts.
- React on a new domain **cannot automatically read** storage from the old HTML or another origin.
- Provide a truthful migration bridge: old app JSON export -> user saves file -> new React import with preview and confirmation -> persisted data reload verification.
- Do not claim one-click automatic import across origins without an explicit, functional bridge.

## 11.2 Backup specification

Use a versioned, portable JSON format with fields or equivalent source-derived data:

```json
{
  "format": "bible-mastery-backup",
  "schemaVersion": 1,
  "exportedAt": "ISO-8601 date",
  "sourceAppVersion": "source-derived version",
  "records": {
    "customScriptures": [],
    "memorisationProgress": [],
    "reviewHistory": [],
    "quizProgress": [],
    "preferences": {}
  }
}
```

This example is **illustrative only**. The actual importer/exporter must account for *every* real persisted source field, including obscure state, active/paused flags, progress and review timestamps. Never erase fields to fit an illustrative schema.

## 11.3 Required migration behaviors

1. Inventory each legacy key and every schema variant actually found; create fixtures from real source exports where possible.
2. Implement original app export support without modifying the immutable original file (a separately versioned legacy export-helper copy may be created, or document existing export capability).
3. Validate file type, structure, schema version, bounded size, required fields, IDs, timestamps, text, and unsupported future versions at import time.
4. Show preview: estimated records, Scripture counts, conflicts, destination and resulting overwrite/merge plan before committing.
5. Provide explicit **merge vs replace** semantics and safe confirmation. Replace requires a recoverable pre-import backup.
6. Preserve exact UTF-8/KJV/user passage text, punctuation, newlines and metadata; no silent normalization of original content.
7. Use transactional writes or a staging/checkpoint/rollback process. A partially failed import must not leave a half-replaced user library.
8. Repeated imports must be idempotent or clearly describe duplicate resolution; no accidental multiplying of passages/progress.
9. Protect against malformed JSON, missing fields, unsupported schema, null values, invalid dates, quota limits, interrupted import, cancelled import and corrupted local state.
10. For same-origin upgrades, create safe versioned migration to IndexedDB **only if justified**, with idempotence and test-driven compatibility. Preserve legacy keys until successful verified restoration and rollback availability.
11. Ensure a user can export again after migration and reload a new tab/browser session to verify persistence.
12. Never send personal Scripture, quiz history, diagnostics or backups to external services automatically.

## 11.4 Recovery and privacy acceptance

- Test source export -> React import -> refresh -> export -> semantic full-field comparison.
- Test pre-import backup restore after a forced failure.
- Test two different Scriptures with independent unfinished progress and pausing states.
- Test long passages, non-ASCII punctuation and newlines.
- Test invalid input has zero destructive side effects.
- Give nontechnical users a short recovery guide, with screenshots where available.

**GATE 3 PASS:** Every supported legacy data class survives export/import or documented same-origin transition with exact field reconciliation and proven rollback. If a schema cannot be migrated yet, do not claim full migration.
